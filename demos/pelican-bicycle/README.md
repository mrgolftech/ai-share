# Demo：鹈鹕骑自行车 —— 模型能力与 Agent Harness 对比

> 用途：AI 大模型与 Agent 工程实践培训  
> 定位：教学演示，不作为正式 Benchmark  
> 状态：已有 Demo 规范；Agent 组第一套正式演示固定使用 ZCode，待实测结果和截图

## 1. 为什么选这个题

“鹈鹕骑自行车”同时满足：

- 任务短，现场容易完成；
- 不是典型后台管理页面模板；
- 需要把“鹈鹕”和“自行车”两个对象正确组合；
- 需要 SVG 几何结构；
- 需要 CSS / JavaScript 动画；
- 结果能直接在浏览器肉眼检查；
- 很适合进一步让 Agent 自己运行、观察和迭代。

因此它不是用来证明“某模型智商更高”，而是用来快速展示：

~~~text
Prompt 理解
+ 代码生成
+ 空间组合
+ 动画逻辑
+ 可执行性
+ Agent 自验证
~~~

## 2. 统一 Prompt

建议固定使用：

> 创建一个单文件 HTML，用 SVG、CSS 和 JavaScript 生成一只鹈鹕骑自行车的循环动画。不得使用外部图片或第三方库。自行车轮子要转动，腿要踩踏板，鹈鹕身体有轻微起伏，画面比例协调、背景简洁，页面保存后可直接在浏览器打开。请直接给出完整可运行文件。

不要针对某个模型额外补提示。

如果第一次失败，先保存原始结果，再进入第二阶段迭代。

## 3. 测试 A：模型能力对比

### 控制变量

尽量固定：

- 同一 Prompt；
- 相同输出长度上限；
- 相近采样参数；
- 不允许联网；
- 不提供参考图片；
- 不允许人工修代码。

### 候选组

建议至少包括：

1. 部门内网 qwen3.6；
2. 一个当前旗舰模型；
3. 一个速度/成本优先的小模型。

具体型号以测试当天实际可用模型为准，不在 Demo 规范中预先写死。

### 观察指标

| 指标 | 0 | 1 | 2 |
|---|---|---|---|
| 指令遵循 | 明显遗漏 | 基本满足 | 全部满足 |
| HTML/SVG 可运行 | 无法运行 | 小修可运行 | 直接运行 |
| 对象组合 | 明显错位 | 基本可辨 | 构图合理 |
| 动画逻辑 | 无/错误 | 部分动作 | 轮子、踩踏、身体协调 |
| 一次完成度 | 不可用 | 有明显瑕疵 | 可直接演示 |

总分只用于这一个 Demo 内部观察，不外推成模型综合排名。

## 4. 测试 B：Chat vs Agent

这里必须使用 **同一个模型**，否则无法区分 Model 和 Harness 的影响。

### Chat 组

只允许：

~~~text
Prompt
→ Model
→ HTML 代码
~~~

由人：

- 复制代码；
- 保存文件；
- 打开浏览器；
- 记录问题。

### Agent 组

第一套正式培训演示固定使用 **ZCode Agent**。后续如需跨 Harness 对比，再保持同模型、同 Prompt、同验收条件增加其他 Agent；不要在这一 Demo 中把多个 Agent 的 UI 混在一起。

ZCode Agent 允许使用：

- Workspace；
- File；
- Shell；
- Browser / Playwright；
- Git（如果在仓库内执行）。

要求 Agent 自己完成：

~~~text
读取目标
→ 创建 index.html
→ 启动/打开
→ 视觉检查
→ 定位问题
→ 修改
→ 再检查
→ 交付
~~~

ZCode 侧重点观察：

- Workspace 是否真实生成文件；
- Built-in Browser 是否被用于查看实际结果；
- Agent 是否根据页面状态继续修改；
- 最终是否进入 Review / Changed Files；
- 当前 Execution Mode；
- 第一次生成是否成功；
- 是否主动运行；
- 是否发现视觉问题；
- 迭代次数；
- 是否真正修好；
- 最终是否留下可运行文件和变更记录。

补充设计见：`demos/zcode-real-world/README.md`。

## 5. 建议现场展示顺序

### 画面 1：只给 Prompt

先问学员：

> 你觉得这是在测“会不会写 HTML”，还是在测更多东西？

### 画面 2：三模型第一次结果并排

不要先公布模型名字。

让大家直接观察：

- 鹈鹕像不像；
- 是否真的坐在车上；
- 轮子是否转；
- 脚是否跟踏板联动；
- 是否有明显穿模和错位。

然后再揭示模型。

### 画面 3：打开代码

说明同样的视觉结果背后还包含：

- SVG path / shape；
- DOM 层级；
- transform-origin；
- keyframes；
- JavaScript 动画或状态更新。

### 画面 4：同模型 Chat vs Agent

这是本 Demo 的关键。

左边：

~~~text
Chat → 给代码
~~~

右边：

~~~text
Agent → 写文件 → 运行 → 看 → 修 → 再验证
~~~

最后引出：

> **模型决定生成能力；Harness 决定模型能否把生成结果接到真实环境里继续完成工作。**

## 6. 结果留档规范

每个模型至少保存：

~~~text
demos/pelican-bicycle/results/
  <model>/
    run-01/
      prompt.md
      raw-response.md
      index.html
      screenshot.png
      notes.md
~~~

Agent 组额外保存：

~~~text
agent-log.md
final-diff.patch
verification.md
~~~

如果后续自动化，应记录：

- 模型名称；
- Endpoint；
- Thinking；
- 温度等采样参数；
- 开始/结束时间；
- Token；
- TTFT；
- 总耗时。

## 7. 演示边界

这个题不能用来得出：

- “模型 A 全面优于模型 B”；
- “开源模型不行”；
- “某 Agent 一定最好”。

正确表述是：

> **在固定 Prompt 和当前运行条件下，这个小任务暴露了不同模型的一次生成差异，也展示了 Agent Harness 在执行、观察和迭代上的价值。**

后续如需正式模型评测，应进入独立的多任务测试集和重复实验。
